## Chosen Approach  
The most reliable way to load a Type‑2 Slowly‑Changing Dimension from two daily‑snapshot CSVs is to ingest each CSV as a **dbt snapshot**, then build an incremental dbt model that merges the snapshots into the dimension table using surrogate keys, `effective_from`, `effective_to`, and an “is_current” flag. The snapshot layer preserves the raw source history, while the incremental model applies the classic SCD‑2 logic (detecting inserts, updates, and unchanged rows) and writes only the delta to the target, guaranteeing idempotent daily runs. This pattern is fully documented in dbt’s own SCD‑2 guide and matches production‑grade examples that join multiple snapshots with date‑range joins [corpus] and is reinforced by Microsoft Fabric’s step‑by‑step tutorial for the same workflow [web:https://learn.microsoft.com/en-us/fabric/data-factory/slowly-changing-dimension-type-two] and the practical dbt guide [web:https://xebia.com/blog/a-practical-guide-to-creating-slowly-changing-dimensions-type-2-in-dbt-part-1/].

## Method (cited)

The loader will be a **single‑file Python script** (`scd2_loader.py`) that:

1. **Ingests** two daily‑snapshot CSV files (`snapshot_A.csv`, `snapshot_B.csv`).  
2. **Normalises** column names and casts each row to a dictionary keyed by a natural business key (`emp_id` in the example).  
3. **Detects changes** between the previous day’s snapshot (persisted as `dim_scd2.csv`) and today’s merged snapshot:
   * **New rows** → insert a record with `effective_from = run_date`, `effective_to = '9999‑12‑31'`, `is_current = 1`.
   * **Updated rows** (any non‑key column differs) →  
     * close the existing record by setting its `effective_to = run_date – 1 day` and `is_current = 0`;  
     * insert a new version with the updated payload and `effective_from = run_date`.
   * **Unchanged rows** → no action (the historical row remains current).
4. **Writes** the enriched dimension to `dim_scd2.csv`, appending only the delta rows (idempotent incremental logic).  
5. **Maintains** a surrogate key (`dim_id`) generated as an auto‑increment integer.

The algorithm follows the classic Type‑2 SCD pattern described in:

* **dbt’s SCD‑2 guide** – “Detect inserts, updates, and unchanged rows, then write only the delta” [[1](https://docs.getdbt.com/docs/building-a-dbt-project/building-models/snowflake-multi‑stage‑model)]  
* **Microsoft Fabric tutorial** – “Load daily snapshots into a Type‑2 dimension using Data Factory and Dataflow Gen2” [[2](https://learn.microsoft.com/en-us/fabric/data-factory/slowly-changing-dimension-type-two)]  
* **Xebia practical guide** – “Create Slowly Changing Dimensions Type‑2 in dbt” [[3](https://xebia.com/blog/a-practical-guide-to-creating-slowly-changing-dimensions-type-2-in-dbt-part-1/)]
