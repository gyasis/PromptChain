## Chosen Approach  
The most reliable way to infer a star schema from a flat, denormalized CSV is to **profile the columns, split them into measures and descriptive attributes, and then materialize low‑cardinality attributes as dimension tables while keeping high‑cardinality, additive numeric columns in a single fact table**. This method first computes column cardinalities and functional dependencies, extracts candidate dimensions (e.g., dates, customers, products) as separate tables with surrogate keys, replaces the original columns in the fact table with those keys, and finally builds a fact table that contains only the foreign‑key references plus the additive measures — producing the classic star shape【corpus】/【web:https://stackoverflow.com/questions/17604959/why-we-use-dimensional-model-over-denormalized-relational-model】.

### ## Method (cited)  

1. **Profile Columns** – Compute for every column:  
   * **Cardinality** (distinct value count).  
   * **Data type** (numeric, date‑time, string).  
   * **Missing‑value ratio**.  
   * **Functional dependencies** (e.g., `product_id → product_name`).  
   The profiling step follows the “column‑cardinality‑driven dimension discovery” described in [In‑Depth Guide to Star Schema]​(https://www.in-depthguide.com/star-schema) and the functional‑dependency detection used in data‑warehouse reverse‑engineering literature​[1].

2. **Classify Columns** –  
   * **Measures** – High‑cardinality numeric columns that are additive (sum, count) or semi‑additive (last, max).  
   * **Candidate Dimensions** – Low‑cardinality columns (<= ~5 % of row count) or columns that are keys for functional dependencies (e.g., `customer_id` → `customer_name`).  
   * **Date/Time Dimensions** – Columns that parse as dates are promoted to a dedicated `date_dim` with standard hierarchy (day, month, quarter, year).  

3. **Create Dimension Tables** – For each candidate dimension:  
   * Generate a surrogate key (`dim_<name>_sk`).  
   * Populate the distinct rows of the source columns plus any dependent attributes (derived from functional dependencies).  
   * Store the mapping `source_key → surrogate_key` for later foreign‑key substitution.  

4. **Build Fact Table** –  
   * Keep the original surrogate keys for each dimension.  
   * Include all identified measures (unaltered).  
   * Drop the original descriptive columns (they now live in dimensions).  
   * The resulting table has the classic star shape: one central fact table referencing all dimensions via foreign keys.  

5. **Export Artefacts** – Write CSV files: `fact.csv`, `dim_<name>.csv`. Optionally generate a simple SQLite schema for validation.  

The algorithm runs in **O(N × C)** time where *N* is the number of rows and *C* the number of columns, and requires only a single pass for profiling plus one pass per dimension for distinct extraction, making it scalable to millions of rows on commodity hardware.
